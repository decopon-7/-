# 給食の未経験食材チェック 設計メモ（v0.1）

依頼者の決定（2026-09-23）：次に作る機能は「給食の未経験食材チェック」。

## 何を解決するか

0〜2歳の園では、**家庭で食べたことのない食材は園で出さない**のが基本（食物アレルギーの事故を防ぐため）。
そのために保護者に「食材チェック表」（家庭で食べた食材に印をつける紙）を出してもらっている。

ところが紙だと、

- 毎日の献立と、子ども一人ひとりのチェック表を **人の目で照らし合わせる** 必要がある
- チェック表が更新されても、配膳する職員に伝わっているとは限らない
- 「照らし合わせた」「その食材を除いた」ことが記録に残りにくい

このアプリでは、**その日の献立 × 子どもごとの「食べたことがある食材」** を自動で照らし合わせ、
配膳の前に「この子はにんじんが未経験」と一覧で出し、**2名で確認した記録** を残す。

## 他社との違い（確認できた範囲）

2026-09-23 に各社の公式サイトなどで確認した範囲：

- コドモン：食事量の記録、アレルギー献立・代替食の管理、献立表の配信がある。食材チェック表は「資料室」に置く文書として使われている例がある
- 給食管理システム（食らぼキッズ）：献立を作る段階で、アレルギー・禁忌食材にアラートを出す
- **子どもごとの「家庭で食べた食材」とその日の献立を照らし合わせ、配膳前に未経験の食材を知らせる機能は、見つけられなかった**

見つけられなかっただけで「どこにもない」とは言い切れない。売り込みに使う前に、各社へ問い合わせて確かめること。

## 安全上の位置づけ（大事）

- **アレルギー対応は、医師の指示書に基づく園の手順が優先**。このアプリは照らし合わせの見落としを減らす補助
- 「除去」の印は、園がすでに把握している除去食材を配膳時に見落とさないためのもの。アレルギーの管理そのものは行わない
- 画面にもこの位置づけを書く

## 画面（「給食」タブ）

| 画面 | できること |
|---|---|
| 配膳前チェック | クラスを選ぶと、今日の献立に **未経験（黄）・除去（赤）** の食材がある子だけを上に出す。問題のない子はまとめて「ほか◯名は問題なし」。「2名で確認して記録」で、確認者2名の名前をタップして記録。確認後に献立や食材の記録が変わったら「確認後に変更あり」と出す |
| 今日の献立 | クラスごとに、今日使う食材をタップで選ぶ |
| 食べた食材 | 子どもを選び、食材をタップするたびに **未 → 家庭で食べた → 除去 → 未** と切り替わる。子どもごとの食材チェック表を印刷できる |

食材の一覧（園の食材チェック表の項目）は、管理者モードで登録する（まとめて貼り付けて登録できる）。

## 決めたこと

- 食べた食材の状態は3つ：**未（記録なし）／家庭で食べた／除去**
- 状態を変えるたびに、誰が・いつ・どの端末で変えたかを履歴に残す（上書きで消さない）
- 配膳前の確認は **2名**（同じ人を2回は選べない）。記録には、確認時点の献立と、対象の子・食材をそのまま残す（あとで献立や食材の記録を変えても、その日の確認記録は変わらない）
- 照らし合わせの計算は、画面とサーバーで同じもの（`app/meals.js`）を使う。確認の記録はサーバーが計算し直して残す
- 給食の記録は通信が必要（午睡と違い、送信待ちには入れない）。つながらない時は、その旨を出して記録しない
- **今日の献立は、食材を1つ選ぶたびに「その食材を足す／外す」だけを送る。** 最初は「選んだ食材ぜんぶ」を毎回送り直す作りにしていたが、2つの食材をほぼ同時にタップすると、あとに送ったはずの内容が消えることがあった（実際にブラウザで再現して確認した）。1件ずつの増減なら、送信が別々の順番で届いても結果は変わらないため、この形にした

## データ（`migrations/0004_meals.sql`）

| 表 | 内容 |
|---|---|
| foods | 食材（名前・分類・並び順・停止） |
| child_foods | 子ども×食材の今の状態（家庭で食べた／除去） |
| child_food_log | 状態を変えた履歴（誰が・いつ・どの端末で） |
| menu_items / menus | クラス×日の献立の食材と、最後に変えた人 |
| meal_checks | 配膳前の確認（確認者2名・時刻・端末・その時点の対象の子と食材） |

## あとでやること

- 保護者用アプリから、保護者が「家庭で食べた」を直接つけられるようにする（今は職員が紙から写す）
- 献立の作成・栄養計算はしない（既存の給食管理の仕組みに任せる）
